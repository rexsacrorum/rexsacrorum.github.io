Where the tokens went

Rules of thumb for an agentic workflow, with the numbers behind them. I measured 25 of my own agent sessions. The main agent re-reading its own history was the largest cost, a fresh reviewer was the cheapest part, and my first count was wrong by a quarter.

Bogdan Novosad · 14 November 2026 · 9 min read

I write almost all my code through a multi-agent workflow. A main agent plans and integrates, and specialist agents implement, review and verify. I had rules for when to delegate. I did not have numbers. The articles I read about agents argued that more agents are better, or that they are a waste, and none of them showed a bill.

So I read my own session transcripts and counted. This article has the numbers, the eight rules I now work by, and what I have not measured. The workflow is public: agent-engineering-workflow is Markdown plus one Python script, wired for Claude Code.

How I measured

Claude Code stores every session as a transcript, with one more transcript for each subagent. Every model request in it records its token counts. I wrote a small read-only command that adds them up per role and model:

python scripts/workflow.py usage <session.jsonl>

I priced the tokens at the public list prices of November 2026. I work on a subscription, so these dollars are a list-price equivalent and not what I paid. They are still a fair unit for comparing one part of a session with another.

I looked at one long session in detail: 23 pull requests on a pre-release prototype, with the main agent on the top model tier and the specialists one tier below. Then I ran the same count over the 25 largest sessions on my machine, across personal and work projects.

Three limits apply to everything below. This is one developer. The sessions did different work, so they cannot show that one way of splitting work is cheaper than another. And the transcript format is internal to the client, so the command stops when a usage record does not have the shape it expects.

The main agent's history is the bill

The main agent was about half of the session. More than half of that half was neither thinking nor writing. It was re-reading. Every request sends the whole conversation again, and the median request in this session carried nearly half a million input tokens of history. Claude Code's best-practices guide describes the same mechanism: a session that has collected several tasks re-reads all of them on every turn of the next one.

This was not special to one session.

What was in that history? In the detailed session, about four fifths of the characters the main agent added to its own history were tool calls and their output: 42% calls and 37% output, not counting screenshots. Everything else, including our whole conversation, was the remaining fifth. The main agent ran 703 shell commands and 74 batches of browser actions itself. The verifier role, which exists to run checks and read logs on a cheaper model, was never called.

A fresh reviewer was the cheapest part

Eight independent reviews cost about 6% of the session, under $3 each before the advisor calls some of them made. A reviewer starts with an empty context, reads the finished diff and returns findings.

I cannot put a number on what those reviews were worth, and I found no controlled experiment that isolates the effect of a reviewer with a fresh context. What exists are vendor reports. Cognition says its review agent finds about two bugs per pull request, more than half of them severe, and works best when it shares no context with the author (Multi-Agents: What's Actually Working). Claude Code's guide says that handing the same task to a subagent does not produce a better answer, but that a fresh reviewer does help, because it has not seen the reasoning.

What I do have is the record of this project. While I was changing the workflow, reviewers with no context found three things I had missed:

  • My cost table was missing a quarter of the cost. That story is in the next section.
  • A safety rule I had written said that a backup script refuses an unsafe destination. On Windows it does not.
  • An installer refused to write through linked folders, as designed, except in its own backup folder.

Each was found by a reader that had not seen how the text or the code was written.

The line I had not budgeted: the advisor

Claude Code has an advisor tool. The working model can consult a stronger model at decision points. Each call sends the whole conversation to the advisor, and that read is not cached (advisor documentation). The detailed session made 45 calls, averaging about 185,000 input tokens each. At list price that is about a quarter of the session. Across the 25 sessions the advisor's share ran from zero to 38%, with a median of 18%.

My first cost table did not have this line at all. The transcript records advisor usage as a separate part of a message, and my script added up only the message's own usage. A reviewer with no context checked the script against the transcripts and found the gap. By then I had already drawn a conclusion from the wrong table: “the main agent is two thirds of the cost” had to become “about half”.

I still use the advisor. But one question to it costs about as much as a whole independent review, so I keep it for decisions that are hard to reverse.

The tier matters less than where the output lands

On the price list I used, a cached read costs the same on the top tier and on the tier below it, $0.20 per million tokens, and half of that on the mid tier. So for a role that mostly reads, moving it down one tier saves at most half of its reading cost. Keeping its output out of the main agent's history removes that output from every later request the main agent makes. In a session of a thousand requests, the second effect is the larger one.

What a subagent gives you is compression. In the detailed session a typical implementer read about 250,000 new tokens and handed back about 2,200. The main agent then re-read roughly 2,200 tokens on each later request, not 250,000.

Those reports were still about 1,500 words each. The workflow now limits a report to about 300 words plus findings and sends logs to a file. I have not measured the effect of that limit yet.

The rules

These are the rules as they stand in the repository, each with the number or source it rests on.

  1. Choose roles by the shape of the task, not its size

    TaskWho writesWho else is called
    Small edit in one areaMain agentNobody
    Substantial change in one areaMain agent, or one implementer from a short contractOne fresh reviewer
    Independent parts on separate pathsOne implementer per partOne fresh reviewer on the whole
    Access rights, a data migration, spendingAs aboveA reviewer, at any size
    Test runs, browser checks, logsNobodyA verifier on a cheaper model

    Anthropic's multi-agent research system used about 15 times the tokens of a chat and paid off on research, which splits into parallel parts. The same post notes that most coding tasks have fewer truly parallel parts (How we built our multi-agent research system). An independent study of 260 configurations found that adding agents changed results by anything from +80.8% on a task that decomposes to −70.0% on sequential planning (Towards a Science of Scaling Agent Systems).

  2. One writer per set of paths

    Parallel writers make conflicting decisions that nobody sees until the merge. Cognition argued against multi-agent systems in 2025 (Don't Build Multi-Agents). A year later it reported that what works is several agents contributing to a task while one of them does the writing.

  3. A reviewer is always fresh and never reused

    Its value is that it has not seen the reasoning. A reviewer that read the first round has. In my session the eight reviews were about 6% of the cost.

  4. Some changes are reviewed at any size

    Access rights, data migrations and anything that spends money. A review costs a few dollars. A miss in these areas costs more.

  5. Every role has a condition under which you skip it

    A subagent first has to rebuild context the main agent already has, and it does not give a better answer to the same task. Skip the implementer when the change depends on what the main agent has just found. Skip the verifier when the check is one short command.

  6. Bulky output goes to a cheaper reader, and reports are short

    Four fifths of what my main agent wrote into its history was tool traffic. Test runs, browser checks and logs belong to a verifier that returns one line per check and a path to the full output.

  7. Waiting should cost nothing

    For a long run, use the client's own notification: a CI monitor, or a background command that reports when it exits. An agent that polls pays the main agent's rate to wait.

  8. A rule lives where the task that needs it will load it

    I had a rule: back up the database before any migration. It lived in AGENTS.md. The repository also had a CLAUDE.md, and when both exist Claude Code reads only CLAUDE.md by default (memory documentation). The workflow skill pointed at the rule, but a small edit never loads the skill. So a one-line migration, the case the rule was written for, would have run without it. The fix was one import line. The general check: for each rule, name the smallest task that needs it and trace what that task actually loads.

Measure, and distrust the count

METR's 2025 trial found that experienced developers took 19% longer with AI tools while believing they had been 20% faster. METR now marks that result as out of date for current tools, and I would not quote the 19% as a fact about today (METR study). The gap between felt and measured speed is the part that lasts. I felt that the reviewer was expensive and the main agent cheap. It was the other way round.

The loop I use is small. One line per finished task goes into a log file: roles called, tokens by role, review findings accepted, and what the review missed. The usage command fills in the tokens. Once a week an agent reads the new lines and proposes at most three changes to the instructions, and I accept or reject them. One warning from Claude Code's guide applies here: a reviewer asked to find problems always finds something, so a count of findings is not a target.

What I am not claiming

  • That delegating more is cheaper. The sessions did different work, and I have no controlled comparison.
  • That review catches a known share of defects. I counted its cost, not its benefit.
  • That these dollars are what anyone pays. They are list-price equivalents.
  • That the new rules work. The report limit and the task table have been in force for days, and the log that will judge them is empty.

Take it

The contract, the roles, the usage command and the sources are in agent-engineering-workflow, under the MIT license. Three things to try, cheapest first:

  1. Run the usage command on your largest session and look at the main agent's row.
  2. Put the “reviewed at any size” line into the file your client loads on every task.
  3. Send test runs and log reading to a cheaper subagent that returns one line per check.
